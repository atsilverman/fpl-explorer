1. Verdict — can we do this?

Yes, with an architecture pivot — not by “just paying for a bigger server,” and not by naively wiring 89 Content Creators into the same 15s pipeline as SoCal.

Realistic assessment Monetizing access to your team + a classic mini-league, plus optional shared cohorts (Content Creators), is achievable while preserving today’s feel — if live data is cached per league, picks are refreshed rarely, and SoCal is isolated from other tenants’ load.
Keep

Static product surface

Vercel static site, Statistics / Ownership / Markets / xData as shared global caches. This already scales with pageviews.

Pivot

Live Home model

Move from one global home_prefs + full-league refetch every ~15s to per-league caches, tiered freshness, and shared cohorts.

Avoid

Naive multi-tenant

Appending every customer’s managers into one mega refresh, or treating Creators as a second SoCal twin at 15s forever.

2. What we have today

The site is a static front end (Vercel) plus a single live Home worker (DigitalOcean) that rebuilds one configured league/manager payload.

Browser ──poll──► Vercel (static UI) │ └── /api/home proxy ──► DO droplet live_server.py (~15s live / ≤1h idle) └── fetch_home.py • bootstrap + live + fixtures (once) • classic league standings • picks (+ often prior GW) per manager • transfers / scoring / ownersByElement └── ONE home_prefs.json managerId + leagueId (SoCal 954157)

Why it feels smooth now

  • League is small (~14) → full refresh finishes comfortably inside the live interval.
  • Switching managers draws from data already in the Home payload / leagues cache.
  • Global pages (ownership, prices, markets) are shared check-ins — not per-user.
  • UI is tuned for one league: fixed HOME_LEAGUE_ID, standings pages, pitch live aura, etc.
Ops detail (including ~30+ FPL requests per refresh for a ~14-manager league) lives in deploy/digitalocean/README.md. This brief is the product/scale companion to that runbook.

3. Content Creators discovery

fplgameweek’s URL shape #/26/team/296817/league/special_10002 was easy to misread: 296817 is the viewing manager, not the league. special_10002 is their curated “Content Creators” table — not an official FPL classic league. FPL classic 10002 is unrelated.

What we collected

site/content_creators_cohort.json — 89 managers with id, fplgameweek displayName, verified FPL playerName / teamName, and https://fantasy.premierleague.com/entry/{id}/ links (same IDs as their chain-icon deep links).

Implication

We cannot leagues-classic/special_10002. Tracking Creators means a cohort: a maintained entry-ID list, standings built from each entry’s points/picks — or finding a real classic league that matches (unlikely).

4. Where stress actually appears

Adding Creators (or N private mini-leagues) does not mainly stress Vercel pageviews. It stresses live Home rebuild cost and upstream FPL.

Surface Today (SoCal) If Creators = same pipeline
Live refresh time Fits ~15s target ~6× work → refresh may exceed interval → sticky / lagged live
FPL API per cycle ~30+ requests Roughly scales with managers (picks × entries, often ×2 GWs + transfers)
Manager dropdown switch Snappy (data in payload) Still snappy if league already loaded
League switch N/A (fixed) Feels like a full Home reload unless caches are warm
Stats / Ownership / Markets Unaffected Unaffected
Payload size Small standings + squads Larger JSON; usually OK if UI keeps paging

Hot path in fetch_home.py today: for each standing entry, fetch GW picks (and often previous GW / transfers), then score. That is correct for a 14-team private league; it is the wrong unit of work to multiply blindly by 89 or by every paying customer.

5. Us vs fplgameweek

They are not “magic hardware.” They are closer to a multi-tenant live cache with progressive loading and shared special leagues.

FPL.db today fplgameweek-style
Tenancy One prefs file → one live job for everyone Many users; caches keyed by league / special league
Content Creators No native equivalent (cohort JSON only) Shared special_10002 for all viewers
Live work Full league picks pull on the poll interval Heavy work amortized; clients read ready payloads; “fetch more teams”
Auth / tiers None Feature levels, Patreon, ads
Front end Static + poll /api/home SPA against Azure APIs
Goal is not to clone their stack. Goal is to copy the scaling idea: compute each league once, serve many readers, keep the focus manager feeling instant.

6. Money: Vercel, DigitalOcean, FPL API

Vercel

Cheap for what it does

Serves static assets and proxies. More visitors reading the site ≈ modest cost. Does not fix live lag. Upgrading Vercel alone is the wrong lever.

DigitalOcean

Necessary, not sufficient

Today ~$6/mo (1 GB) runs one poller. A larger droplet buys headroom so one job finishes faster. It does not fix FPL rate limits or “N full leagues × 15s” without design changes.

Spend lever What it buys What it doesn’t
Bigger DO droplet CPU/RAM for 1–few live leagues; fewer timeouts Unlimited private leagues at SoCal smoothness
Vercel Pro / bandwidth Static scale, previews, team features Faster mini-league live scoring
Shared league caches (eng time) Many users on one Creators/SoCal job ≈ near-zero marginal cost per viewer —
Naive “every customer = full 15s job” Short-term demos Sustainable product; hurts existing customers first

Cost grows with distinct live leagues being fully refreshed, not with raw pageviews. Upstream FPL is the hard ceiling — treat it as a scarce resource.

7. Strategies (A / B / C)

Three coherent options. Recommended path is B, with pieces of A early and C only if needed.

Strategy A — Dual league, single-tenant (near-term)

You + friends: SoCal and Content Creators

  • UI: league dropdown + cascading manager dropdown (settings / onboarding).
  • SoCal: keep classic 954157 full live as today.
  • Creators: load from content_creators_cohort.json; do not poll all 89 at 15s initially.
  • Creators freshness: focus manager fast; rest of cohort slower or on-demand; or “snapshot” mode between matchdays.

Pros: Ships the UX you want; low risk to SoCal.
Cons: Still one operator’s prefs; not a paywall yet.

Strategy B — Per-league live cache (recommended for monetization)

Multi-reader, few writers

  • Key caches by leagueId or cohort:content_creators.
  • GET /api/home?league=…&manager=… reads that cache; manager switch is mostly client-side.
  • Shared cohorts (Creators) computed once for all subscribers.
  • Private classic leagues: one job per league ID; two customers in the same league share one job.
  • Priority queue: SoCal / paid SLAs ahead of bulk cohort backfill.

Pros: Same smoothness for small classic leagues; Creators amortized; paywall-ready.
Cons: Real eng work — prefs, API shape, worker, isolation. Not a config tweak.

Strategy C — Full SaaS rebuild

Auth, billing, self-serve league attach, horizontal workers

  • Accounts, Stripe, self-serve “add league ID,” automated caps, observability.
  • Multiple workers / queues; maybe Redis; proper rate-limit handling.

Pros: True product scale.
Cons: Large rebuild; premature before Strategy B proves demand.
When: After manual onboarding is painful and revenue justifies it.

What is not a strategy Wiring Creators into tracked_ids + forcing fetch_home every 15s for 89 entries while still using one global prefs file. That copies today’s shape and multiplies pain.

8. Live refresh tactics

Staggering batches (managers 1–20 this tick, 21–40 next) helps spread FPL load. It is incomplete alone. The higher-leverage split:

Data Suggested cadence Why
Bootstrap + /event/{gw}/live ~15s while fixtures live One feed; rescore everyone’s known squads
Focus manager picks Fast (or on switch) Pitch / chips must feel live
Other managers’ picks Rare (deadline, chip, detected change) or 45–120s staggered Picks barely change mid-match
League standings order Derived from cached picks + live points Avoid full entry history storms
Transfers / chips tables Slower Not second-critical
Today’s live interval can overlap itself if one full fetch exceeds 15s. Bigger hardware delays the problem; tiered refresh + concurrency limits fix it. Live server already has a long fetch_home timeout — treat overruns as a product bug, not “needs more RAM.”

9. Paywall & onboarding model

Desired early model: customer submits manager ID + classic league ID; you configure access. That is fine — if capacity is explicit.

Three layers

1 · Global

Shared for everyone

Ownership, prices, markets, calendar, Statistics bundle. Already scales.

2 · League live

The paid unit

Cache per classic league or cohort. Many readers, one writer job.

3 · User prefs

Tiny

Which manager + which league cache. Not a full data rebuild by itself.

Manual onboarding checklist

  • Prefer official classic league IDs (standings API) over huge hand lists.
  • Size caps: e.g. ≤20 full live; 21–50 slower live; 50+ cohort/diluted or reject.
  • Content Creators = optional shared add-on, one cache for all who enable it.
  • Do not merge customers into one mega tracked_ids / one prefs file.
  • Activate new mid-sized leagues off-peak when possible; never starve SoCal’s worker.
  • Document freshness in the product (“focus 15s · league ~60s”) so expectations match physics.

Protecting existing customers (SoCal)

  • Isolate SoCal’s refresh from other leagues (priority queue or dedicated slot).
  • Don’t let a 50-team onboarding job block the shared 15s SoCal cycle.
  • Measure: refresh duration, FPL error rate, time-to-fresh for focus manager.

10. Keeping SoCal-level UX

The bar is: pitch live feel, standings that move, manager switch without thinking, league EO / “who owns X,” viewing another manager’s squad — all as smooth as today for small classic leagues.

Preserve
  • Client manager switch over warm league payload
  • Standings paging / existing Home chrome
  • Live aura / pts treatment on pitch
  • Static pages independent of Home live
Accept (for huge cohorts)
  • Slightly slower “rest of league” ticks
  • League switch = brief loading state
  • Creators EO as best-effort vs SoCal precision
  • Honest freshness labels in UI

Mimicking fplgameweek’s feel does not require their full Azure stack — it requires never making the user wait on 89 serial picks pulls to paint their own pitch.

11. Pivot vs rebuild checklist

Area Needed? Notes
Front-end pages (Stats, Ownership, …) No rebuild Keep; cache-bust as today
Home UI components Extend League + manager dropdowns; loading/freshness affordances
HOME_LEAGUE_ID hardcode Must pivot Unfix prefs / applyLeagueId / live eligibility checks
fetch_home.py Pivot Support cohort sources; picks cache; optional partial refresh
live_server.py Pivot Multi-cache or query params; priority; no single prefs god-object
Auth / Stripe / self-serve Later (Strategy C) Not required for first paid customers if onboarding is manual
Scraping fplgameweek ongoing Avoid as dependency Use our cohort file; refresh IDs periodically by hand or export
Bottom line on rebuild You do not need to throw away the site. You do need to stop treating “live Home” as one global static prefs + full-league refetch. That is a focused backend/API pivot with UI dropdown work — not a greenfield rewrite.
